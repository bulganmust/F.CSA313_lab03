## 1. Гурван чанарын сценарио (6 хэсэгтэй формат)

### 1.1 Performance сценарио — `/cart/add` хариу хугацаа

| Хэсэг | Агуулга |
| --- | --- |
| **Тойм** | Хэрэглэгч сагсанд бараа нэмэхэд систем хурдан хариулах ёстой. |
| **Системийн төлөв** | `server.js` хэвийн ажиллаж байна, гурван endpoint бүгд идэвхтэй. |
| **Орчны төлөв** | Локал машин, хэвийн ачаалал: 20 VU тогтмол, VU бүр ~1.3 секунд тутам нэг давталт хийх тул ≈ 15 хүсэлт/с (`/cart/add`-д), 1 минут. |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /cart/add` илгээнэ. |
| **Шаардлагатай хариу** | Систем `200 OK` ба `{"ok":true,"items":1}` буцаана. |
| **Хэмжүүр** | Хүсэлтийн 95% нь **20 мс-ээс бага** (p95 < 20 мс), 20 VU, 1 минутын дотор. |

### 1.2 Reliability сценарио — `/pay` эвдрэлийн давтамж

| Хэсэг | Агуулга |
| --- | --- |
| **Тойм** | Хэрэглэгч төлбөр хийхэд ховор тохиолдолд л алдаа гарах ёстой. |
| **Системийн төлөв** | Сервер хэвийн ажиллаж байна, төлбөрийн gateway хэсэгчлэн найдваргүй (кодонд ~5% алдаа суулгасан). |
| **Орчны төлөв** | 20 VU тогтмол ачаалал, ≈ 15 `/pay` хүсэлт/с, 1 минут (≈ 930 хүсэлт). |
| **Гадаад өдөөлт** | Хэвийн хэрэглэгч `POST /pay` илгээнэ. |
| **Шаардлагатай хариу** | Систем `200` ба `{"paid":true}` буцаана; тохиолдлын багахан хэсэгт `500` буцаана. |
| **Хэмжүүр** | POFOD (Probability of Failure On Demand): `/pay` хүсэлтийн алдаа гарах магадлал **< 8%** (`http_req_failed{name:pay}`), 1 минут, 20 VU. |

### 1.3 Availability сценарио — серверийн гэнэтийн зогсолт

| Хэсэг | Агуулга |
| --- | --- |
| **Тойм** | Сервер гэнэт зогсоод дахин асахад хэрэглэгчид ихэнх хугацаанд үйлчлүүлж чадах ёстой. |
| **Системийн төлөв** | Сервер ажиллаж байгаад тестийн явцад процесс нь зогсоно (crash). |
| **Орчны төлөв** | 20 VU тогтмол ачаалал, 2 минутын цонх. |
| **Гадаад өдөөлт** | **Эвдрэл:** `node server.js` процессыг Ctrl+C-ээр зогсоож, 10 секунд хүлээгээд дахин асаана. |
| **Шаардлагатай хариу** | Дахин асмагц систем хүсэлт хүлээн авч эхэлнэ; зогсолтын үед хүсэлт connection refused-ээр шууд алдаа буцаана. |
| **Хэмжүүр** | Амжилттай хүсэлт / нийт хүсэлт **≥ 90%** (2 минутын цонхонд), сэргэх хугацаа **≤ 12 секунд** (120 с × 10%). |

**"Сайн сценариогийн 5 шинж"-ээр өөрийгөө шалгасан нь:** итгэмжтэй (өөрийн серверийн бодит зан төлөвөөс гаргасан), үнэ цэнэтэй (төлбөр, сагс гэх мэт бизнесийн үйлдэл), тодорхой (endpoint, VU, хугацаа заасан), нарийн (тоон хэмжүүртэй), ойлгомжтой (6 хэсэгт тус тусдаа).

## 2. SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | `slo-test.js` дахь threshold |
| --- | --- | --- | --- | --- |
| Performance | `/cart/add` latency | **p95 < 20 мс** | 20 VU, 1 мин | `'http_req_duration{name:cart}': ['p(95)<20']` |
| Reliability | `/pay` error rate | **< 8%** | 20 VU, 1 мин | `'http_req_failed{name:pay}': ['rate<0.08']` |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | **≥ 90%** | 2 мин, 10 с зогсолттой | `'checks': ['rate>0.90']` |
| Нэмэлт (4 дэх): Performance | `/report` latency | **p95 < 450 мс** | 20 VU | `'http_req_duration{name:report}': ['p(95)<450']` |

> **Тайлбар:** `slo-test.js` дахь `duration` нь одоо `'2m'` (chaos туршилтын тохиргоо). PASS туршилтыг ижил скриптээр `duration: '1m'` болгож ажиллуулсан (`results/pass.txt` дахь `20 VUs 1m0s`), threshold-ууд хоёр үед ижил.

### Босго сонгосон үндэслэл

- **Cart p95 < 20 мс:** localhost дээр бодит p95 ≈ 2 мс байдаг тул анхны `200 мс` нь юу ч хэмжихгүй сул босго болно; 20 мс нь хэвийн утгаас ~10 дахин өндөр тул машины жижиг савалтад худал дохио өгөхгүй ч бодит регресс (жишээ нь давхар DB дуудлага) гарвал барина.
- **Pay < 8%:** серверт 5% алдаа суулгасан. ~930 хүсэлтийн түүврийн стандарт хазайлт ≈ 0.7% тул 8% нь 5%-иас ~4σ дээр — санамсаргүй хэлбэлзлээс болж худал FAIL өгөхгүй, харин алдааны хувь хоёр дахин өсвөл барина (`pass.txt`-д бодит утга 5.48%).
- **Availability ≥ 90%:** 2 минутын цонхонд 10 секундын зогсолтыг тэсвэрлэхээр сонгосон (доорх error budget-ийг үз).
- **Report p95 < 450 мс:** сервер `/report`-д 200-400 мс санамсаргүй хүлээдэг тул бодит p95 ≈ 390 мс (`pass.txt`: 388.99 мс); 450 мс нь ~15% нөөцтэй.

### Error budget тооцоо (availability, 90% SLO)

- **Цагаар:** 2 мин = 120 с × 10% = **12 секундийн** "эвдрэх эрх".
- **Хүсэлтээр:** chaos туршилтын нийт 5751 хүсэлт × 10% = **575 хүсэлтийн** budget (Алхам 5-д харьцуулна).

## 3. PASS туршилт (`results/pass.txt`)

Команд: `mkdir -p results && k6 run slo-test.js 2>&1 | tee results/pass.txt`

| Threshold | Босго | Бодит утга | Үр дүн |
| --- | --- | --- | --- |
| `http_req_duration{name:cart}` | p(95) < 20 | 2.66 мс | ✓ |
| `http_req_duration{name:report}` | p(95) < 450 | 388.99 мс | ✓ |
| `http_req_failed{name:pay}` | rate < 0.08 | 5.48% (51 / 930) | ✓ |
| `checks` | rate > 0.90 | 98.17% | ✓ |

Бүх threshold ✓ (PASS). `results/pass.txt`-д сонгосон 1 минутын туршилтаар 930 iteration, 2790 request ажилласан; бүх threshold PASS болсон. Босгыг PASS болгохын тулд биш, сценариогийн бодит утгад тааруулан сонгосон.

## 4. Chaos туршилт — availability сценариог бодитоор турших (`results/chaos.txt`)

Команд: `k6 run slo-test.js 2>&1 | tee results/chaos.txt` (`duration: '2m'`). Тест ажиллаж байхад серверийг Ctrl+C-ээр зогсоож, 10 секунд хүлээгээд `node server.js`-ийг дахин ажиллуулсан.

### Хэмжсэн тоо

| Хэмжүүр | Утга |
| --- | --- |
| Нийт хүсэлт (`http_reqs`) | 5751 |
| Нийт checks | 5751 |
| Амжилттай checks | 4788 (**83.25%**) |
| Амжилтгүй checks | 963 (16.74%) |
| `cart 200` | 1622 / 1917 (84%) |
| `report 200` | 1622 / 1917 (84%) |
| `pay 200` | 1544 / 1917 (80%), алдаа 19.45% |

### Threshold-ын үр дүн

- **Availability (`checks`, rate > 0.90):** бодит **83.25%** → **✗ FAIL**.
- **Reliability (`http_req_failed{name:pay}`, rate < 0.08):** бодит **19.45%** → **✗ FAIL**.
- **Cart latency** (`p(95)<20`): p95 = **2.06 мс** → ✓ PASS.
- **Report latency** (`p(95)<450`): p95 = **389.42 мс** → ✓ PASS.
- k6 төгсгөлд `thresholds on metrics 'checks, http_req_failed{name:pay}' have been crossed` гэж мэдээлсэн: зөвхөн availability ба reliability threshold зөрчигдсөн.
- Latency threshold-ууд зогсолтод мэдрэгдээгүй: `connection refused` хүсэлт агшин зуур буцдаг тул p95-д нөлөөлсөнгүй. Иймд latency SLO дангаараа зогсолтыг илрүүлж чадахгүй, availability-д тусдаа SLI хэрэгтэй.

### Бодит availability ба error budget

Availability = амжилттай хүсэлт / нийт хүсэлт = 4788 / 5751 = **83.25%** < 90% SLO.

- **Хүсэлтээр:** budget 5751 × 10% = **575** хүсэлт. Бодит унасан **963** → budget-ээ **388 хүсэлтээр хэтэрсэн**.
- **Цагаар:** budget 12 секунд. `results/chaos.txt` дахь k6-ийн `connection refused` анхны (`22:00:53`) ба сүүлийн (`22:01:08`) мөрөөр сервер ~**15 секунд** унасан (10 с хүлээлт + `node` дахин асах хугацаа) → budget-ээ ~**3 секундээр хэтэрсэн**.

### Яагаад цаг ба хүсэлтээр тооцсон budget зөрж байна вэ

k6-ийн `checks` нь ЦАГИЙН биш ХҮСЭЛТИЙН хувь. Сервер унасан үед хүсэлт агшин зуур `connection refused`-ээр буцдаг тул `/report`-ын 200-400 мс хүлээлт алга болно, VU бүр зөвхөн `sleep(1)`-ээр саатан ≈ 1 секундэд нэг давталт хийнэ. Хэвийн үед давталт ≈ 1.3 секунд (`/report` 300 мс орсон) байдаг. Иймд зогсолтын нэг секунд хэвийн секундээс ~30% илүү хүсэлт "иддэг":

- Цагийн хувь: 15 с / 120 с ≈ **12.5%**.
- Зогсолтод унасан давталт: cart 1917 − 1622 = **295** давталт → 295 / 1917 ≈ **15.4%**. (Дундаж ≈ 295 / 15 с ≈ 20 давталт/с, хэвийн үед ≈ 15/с.)
- Нийт 963 алдаа = 295 (cart) + 295 (report) + 373 (pay). Pay-ийн 373-аас 295 нь зогсолтоос, үлдсэн **78** нь серверт суулгасан ~5% алдаа (78 / 1622 ≈ 4.8%).

Тиймээс 963 = 3 × 295 + 78. Нэг зогсолт хүсэлтийн тоогоор цагийн хувиас илүү хүнд тусдаг.

### Reliability threshold яагаад мөн FAIL болсон бэ

Сервер бүхэлдээ унасан үед `/pay`-д илгээсэн хүсэлт бүр `connection refused`-ээр алдаа буцаасан тул availability-ийн эвдрэл reliability SLI-г шууд зөрчсөн: нэг эвдрэл хоёр SLO-г зэрэг зөрчив. **Тусгаарлах арга:** availability-г холболтын түвшний алдаагаар (status 0 / health-check probe), reliability-г зөвхөн серверээс ирсэн HTTP 5xx-ээр (status ≥ 500) хэмжвэл хоёр SLI хамаарахгүй болно. Дээрх задаргаагаар зогсолтыг хассан `/pay` алдаа ≈ 4.8% нь суулгасан 5%-тай таарч байна.

### Дүгнэлт: SLO хэт өөдрөг байсан уу, зогсолт хэт урт байсан уу?

Хоёулаа. Гараар restart хийхэд 10 биш ~15 секунд зарцуулагдсан нь 12 секундийн budget-ийг хэтрүүлсэн. Гэхдээ зөвхөн 10 секундийн зогсолт байсан ч (≈ 10 с × 20 давталт/с × 3 хүсэлт ≈ 600 хүсэлт + ~80 суурь pay алдаа ≈ 680 / 5751 ≈ 11–12%) хүсэлтээр 90%-ийн SLO зөрчигдөх байсан (тооцооллын ойролцоо). Иймд "2 минутад 10 с зогсолт → 90%" гэсэн SLO нь хүсэлтийн хувиар хэт өөдрөг байсан.

## 5. Зориуд FAIL болгох (`results/fail.txt`)

`slo-test-fail.js` нь `slo-test.js`-ийн хуулбар бөгөөд `duration: '1m'` ба `/report` threshold `p(95)<100` гэсэн хоёр өөрчлөлттэй:

```
http_req_duration{name:cart}    : ['p(95)<20']
http_req_duration{name:report}  : ['p(95)<100']
```

Команд:

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; code=${PIPESTATUS[0]}; echo "exit=$code" | tee -a results/fail.txt
```

### THRESHOLDS блок (fail.txt-ээс)

```
http_req_duration{name:cart}
✓ 'p(95)<20' p(95)=2.15ms

http_req_duration{name:report}
✗ 'p(95)<100' p(95)=391.61ms

http_req_failed{name:pay}
✓ 'rate<0.08' rate=5.59%

checks
✓ 'rate>0.90' rate=98.13%
```

- **FAIL-ийг харуулсан мөр:** `✗ 'p(95)<100' p(95)=391.61ms` ба `level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"`.
- **Exit code:** `exit=99`. k6 threshold зөрчигдвөл 99 кодоор гардаг; CI pipeline яг энэ кодоор build-ийг зогсооно.
- `/report` нь 200-400 мс санамсаргүй хүлээдэг тул (бодит p95 = 391.61 мс) 100 мс-ийн босго ямар ч машин дээр найдвартай FAIL болно.
- `✗ pay 200 (52/930)` нь threshold-ын FAIL биш, серверт суулгасан ~5% алдааны *check* юм (5.59% < 8% тул reliability threshold PASS).
- Хэрэв `/cart/add`-ыг `p(95)<50` болговол localhost дээр (бодит p95 ≈ 2 мс) PASS хэвээр үлдэнэ: сүлжээний зай байхгүй, endpoint шууд JSON буцаадаг тул 50 мс нь ч сул босго.

### Exit code-ийн анхаарах зүйл

Анх `k6 run ... | tee results/fail.txt; echo "exit=$?"` гэж ажиллуулахад `exit=0` гарсан. Шалтгаан: pipe-ийн дараах `$?` нь **хамгийн сүүлийн командын** (`tee`) кодыг өгдөг, k6-ийнх биш. Иймд `${PIPESTATUS[0]}` (эсвэл `set -o pipefail`) ашиглан k6-ийн жинхэнэ `99` кодыг авсан. CI-д үүнийг мартвал threshold зөрчигдсөн ч build "ногоон" гарна.

## 6. Дүгнэлт

Сценариогоос SLO, SLO-оос threshold руу шилжихэд хамгийн хэцүү нь босгыг "юу ч хэмжихгүй сул" биш, бодит утгад тааруулж сонгох байсан: localhost дээр `/cart/add` p95 ≈ 2 мс тул анхны 200 мс-ийн босго утгагүй, 20 мс болгосноор л утга учиртай болсон. Хоёр дахь хүндрэл нь SLO-г цаг, хүсэлт гэсэн хоёр өөр нэгжээр тооцоход гарсан: цагаар 12 секундийн budget байхад хүсэлтээр 575 болж, k6-ийн `checks` нь цагийн биш хүсэлтийн хувь тул зогсолт хэвийн үеэс илүү хүсэлт "иддэг". Chaos туршилт availability сценариогийн хэмжүүрийг **үгүйсгэв**: бодит availability 83.25% гарч 90%-ийн SLO-г, 15 секундийн сэргэлт 12 секундийн budget-ийг хэтрүүлсэн. Түүнчлэн зөвхөн 10 секундийн зогсолт байсан ч хүсэлтийн хувиар 90%-д багтах нь эргэлзээтэй байсан тул SLO нь хэт өөдрөг байсан. Нэг эвдрэл availability ба reliability гэсэн хоёр SLO-г зэрэг зөрчсөн нь SLI-г холболтын алдаа, HTTP 5xx гэж тусгаарлах хэрэгтэйг харуулсан. Зогсолтыг хассан `/pay` алдаа ≈ 4.8% нь суулгасан 5%-тай таарсан нь тооцооны зөв байдлыг баталсан. FAIL туршилтаар k6 threshold зөрчигдвөл exit code 99 буцааж CI-г зогсоодог нь батлагдсан. Мөн `| tee` pipe нь k6-ийн exit code-ийг далдалж `0` харуулдаг гэдгийг өөрийн алдаагаар сурсан. Дараагийн удаа сервер restart-ыг гараар биш автоматаар (жишээ нь process manager) хийж, availability-г цагаар болон хүсэлтээр зэрэг хэмжиж, SLO-г тэр хоёрт тааруулан сонгоно.
